# Full audit — data, domain, providers, interface

A pass over the whole project looking for defects rather than adding features:
the JSON data (integrity, citations, localization), the domain layer (rules,
lookups, validators), the Riverpod providers, and the widget layer. Fourteen
defects were found and fixed; four screens that had not been looked at since the
type scale changed were checked on screen.

## Behavioural defects

| # | Where | What was wrong |
|---|---|---|
| 1 | `consist_providers.dart`, `placementResultsProvider` | `ref.watch` was called **after an `await`**, inside the per-placement loop. Riverpod forbids it — the provider may already be disposed. Invisible with one vehicle (the first pass watches before awaiting) and live from the second onwards, which is exactly the two-vehicles-on-one-wagon case. Every watch is now hoisted above the loop. |
| 2 | `schematic_hit_test.dart` | `spacerBoard` was in `_rectKinds`, but `_pairElements` gives hardware two points at the **same x** — so its "rectangle" was zero-width and the insert block was the one hardware kind that could never be tapped. |
| 3 | `consist_providers.dart`, `wagonBudgetProvider` | Vehicles were ordered with `List.sort` on `offset.dx`. Dart's sort is **not stable** and every offset is 0 until something is dragged, so which vehicles counted as neighbours — and therefore whether a 100 mm or a 270 mm clearance applied — could change between rebuilds. Ties now keep placement order. |
| 4 | `wagon_budget_panel.dart` | The gap count was derived as `totalClearance / largestGap`, so a load with a 100 mm and a 270 mm gap reported "1 gap". `WagonLengthBudget` now carries `gapCount`. |
| 5 | `placement_screen.dart`, `consist_providers.dart` | Deleting a vehicle cleared its equipment and securing method but **not** its chock arrangement; rebuilding the train (changing wagon count or type) dropped placements while all three maps kept their entries. All three are now pruned to live placements. |
| 6 | `engineering_validator.dart` | A wheeled vehicle with no recorded combat weight — every lorry in the catalogue — resolved **no hardware and no check at all**. The plate requires quadrilateral chocks for a wheeled vehicle whatever it weighs, so the chock is now always required and the lashing count reports UNKNOWN instead of silence. |
| 7 | `engineering_validator.dart` | The wheeled lashing count was hardcoded (`w <= 24 ? 4 : ...`) beside `requiredWireLashingCount`, which reads the same brackets from `rules.json` — two copies of one rule. |
| 8 | `equipment_catalog.dart`, `equipment_selection.dart` | A wheeled vehicle was offered — and could be scored against — the **tracked** chock table. Table 3 sizes by combat weight; Table 2 sizes a wheeled vehicle's chock by wheel diameter. |
| 9 | `weight_bracket.dart` | The bracket parser could not read Table 2's wordings (`"under 500"`, `"1600 and above"`); they matched nothing, silently. Renamed `valueMatchesRange` since it reads millimetres as readily as tonnes. |
| 10 | `chock_arrangement_catalog.dart` | Tracked seating cases were built with `spansCoupling: false` hardcoded, so a tracked vehicle placed over a coupling **failed its arrangement check whichever case was chosen**. |
| 11 | `vehicle_category_screen.dart` | The category card's fixed `300x340` was cut for the old 13 px text and overflowed by 17 px at the new scale — confirmed on screen, now `320x410`. |

## Data defects

| # | What |
|---|---|
| 12 | **Nine citations pointed at paragraphs with no entry** (`para-5`, `-35`, `-36`, `-38`, `-39`): tapping them showed a raw id and no text. The five entries were added with their real paragraph numbers. Para. 5 carries the conditional-wagon accounting the project's own `platforms.json` notes already quote; the other four say explicitly that the paragraph's text was not extracted, because inventing it is exactly what this project refuses to do. |
| 13 | **Twenty-two entities had no Turkmen text** — 10 vehicles, 1 platform, 3 hardware types, 8 rules — so English appeared inside an interface that is otherwise entirely Turkmen. All translated. |
| 14 | **The half-round insert block had no equipment catalogue**, so method 5's second component showed "no options" while plate-02 dimensions it (90-100 mm high, 300-400 mm long). Added as `insertBlockTable`, cited. The two clamps still have none, correctly: the source gives no sizing table for them. |

## Smaller corrections

- `ReferenceLinker.photosForAny` returned photos in `photos.json` order while its
  doc promised the caller's id order (which carries meaning — a hardware id's own
  citation first, then the evidence-based extras).
- `filterVehicles` searched only English text; a Turkmen search term could not
  match a vehicle, though the principle and rule filters already searched their
  Turkmen fields.
- The wagon-type step would build a train of **zero wagons** if step 1 was
  skipped, landing on a placement screen with nowhere to put anything. It now
  says so and sends the user back to step 1.
- `getRuleEntries()` was the only repository getter with no cache — it re-read
  and re-merged the Turkmen rules file on every call, including on every
  securing-screen rebuild.
- `AppText.drawing` was defined, documented and unused; painters set their own
  sizes deliberately, and the class now says that instead of implying a floor
  nothing enforced.

## New guards

`test/data_integrity_test.dart` fails if **any** citation points at an id absent
from `references.json`, if any entity ships without Turkmen text, if a
translation is left behind for a deleted entity, if a reference names a section
that does not exist, or if a vehicle approves hardware that is not in the
catalogue. Both of the data defects above would have been caught at their
introduction by these.

Regression tests also cover the spacer-board hit box and the mixed-load gap
count. The suite is **310 tests** after the improvements below.

## Checked and deliberately left alone

- `securing_screen.dart`'s `placements.first` is guarded by an earlier empty
  check — not a crash risk.
- A coupling-spanning vehicle is still drawn on both wagons' diagrams: it does
  rest on both, and the placement row labels it. Only the double-*counting* in
  the deck budget was wrong, and that is fixed.
- The "PDF HASABATYNY ÇYKAR" button on the result screen was an honest stub
  saying the export module was not implemented. It is implemented now — see
  improvement 3 below.

## Coverage of these fixes

The provider-level regressions (1, 3, 5) were verified by reading and on screen
when this audit was written, because `flutter test` did not run on this machine.
It does now (see improvement 4), and they are covered by
`test/placement_providers_test.dart`.

# The six improvements, built

## 1. Instructor-supplied figures

Every rule that mattered was starved: **no vehicle in the extract carries a
combat weight, and none carries a length**, so the KGUUB bracket, the chock
size, the wheeled chock count, the lashing count and the deck budget all
reported "cannot be decided" for every load.

`Vehicle.withUserSuppliedFigures` fills an empty field with a figure the
instructor typed and records which fields those were in `userSuppliedFields`.
`effectiveVehiclesProvider` applies them and is what the whole engineering path
now reads; `vehiclesProvider` stays the untouched catalogue, so the reference
browser keeps showing what the handbook says. A figure already in the extract
is never overwritten — the handbook always wins — and anything resting on a
typed figure is badged **EL BILEN GIRIZILEN**. The weight can be given exactly
where the app says it is missing, under the securing-method note.

## 2. Score and mistake log

`scoreAttempt` counts passes and failures across every placement *and* the
consist-level checks, and holds one line: **an undecided check is never counted
as correct.** Most checks here are undecided for want of a figure the source
does not give, so a score that rolled them in would award a good mark for a
configuration nobody has verified. Undecided checks are reported on their own
line and kept out of the percentage entirely; `AttemptScore.isClean` is false
when nothing could be decided at all.

Wrong actions that never become a check — tapping a wagon that cannot be loaded
— are recorded as `AttemptEvent`s with their citation. Failed checks are *not*
logged separately: a FAIL already is a mistake, and counting it twice would
punish it twice.

## 3. The four unused dependencies, decided

`pdf` and `path_provider` are now used: the result sheet is built as a real PDF
and written to the documents directory, with the bundled Noto font embedded —
the package's built-in Helvetica has no ä ň ö ü ý ş ž, so the Turkmen sheet
would otherwise print as tofu. `printing` and `sqflite_common_ffi` are
**removed**, along with the sqlite build hook: these machines may have no
printer configured, and an instructor wants a file, not a print dialogue.

The result-screen button that used to answer "not implemented" now writes the
file and reports its path.

## 4. The test environment

`flutter test` **works**. The old failure — every file reporting a websocket
503 against `127.0.0.1` — was never a code problem: a proxy was intercepting
the loopback connection to `flutter_tester`. With `no_proxy` set for localhost
the whole suite runs.

That unlocked the tests that could not be written before, and
`test/placement_providers_test.dart` now covers precisely the defects that
slipped through the gap: results building for **two** placements, per-placement
state pruned on delete and on rebuild, a wheeled vehicle resolving chocks with
no weight, an instructor's weight reaching the engineering path, and the deck
budget charging one gap. Flutter-dependent tests carry `@Tags(['flutter'])`;
`dart test --exclude-tags flutter` still runs the pure-Dart majority.

## 5. Content coverage

Photographs were fetched for the three lorries (ZIL-131, KamAZ-43114,
Ural-4320), taking the catalogue from 14 photographs to 17 and from 7 clean
cut-outs to 9. The KamAZ cut-out was rejected: it keeps a strip of blue fence
behind the cargo bed, and a fence riding on the wagon deck is worse than no
photograph.

**A correction to an earlier claim of mine:** the nine object-index entries are
*not* empty records. Each carries a handbook-mandated iron spur type from
Table 13 — Ş-575, Ş-429, Ş-137 and so on — which makes them the best-determined
group in the catalogue for the securing question, even though they have no
dimensions at all. Rather than hiding them, their card now names the mandated
type instead of leaving a "0% data" badge to speak for them.

## 6. Consist-level rules

Three rules that existed only as data now run. `consistChecksProvider` evaluates
the **deck budget** for each loaded wagon, the **guard wagon** requirement
(plate-05: an overhang past 400 mm requires one), and the **echelon class**
(para. 5: 40 conditional wagons up to 1500 t, 57 up to 3000 t) — and all of
them count in the score, so an overloaded wagon can no longer sit inside a
clean attempt. The tonnage side of the echelon rule stays UNKNOWN, because it
needs each wagon's net load and no vehicle carries a weight; the check says so
rather than adding up zeroes.

The result screen also had to become scrollable — the score panel and the
mistake list ran 392 px off the bottom of the window.

# Second type-scale pass — bigger again, and easier to use

The scale was raised a second time, in one edit, because everything letters
itself from `AppText`:

| | before | now |
|---|---|---|
| body | 15 | **17** |
| small body | 13.5 | **15** |
| label | 14 | **16** |
| caption | 12 | **13.5** |
| section title | 15 | **17** |
| card title | 19 | **22** |
| screen title | 21 | **24** |
| display / counter | 30 / 56 | **34 / 66** |

Controls grew with it — a taller app bar, more padding in buttons, text fields
and text buttons, 26 px icons — because text that grows while its targets do
not is harder to use, not easier. Labels lettered onto the diagrams went up a
point too but stay below the interface scale on purpose: inside a drawing, a
name at interface size covers the thing it names.

Every fixed-size layout that was cut for the old scale was grown with it: the
vehicle grid (520x480 tiles, 132 px photos), the category card (350x460), both
reference grids, and the securing screen's placement picker.

**Checked on screen, not assumed.** A scripted tour walked all ten screens with
a two-wagon train loaded, and the run logged no overflow anywhere. Two real
problems turned up in the pictures rather than the logs:

- On a selected vehicle card the quantity badge sat **on top of** the card's own
  "✓ SAÝLANDY" label — both start at the top left. The badge moved to the top
  right.
- A selected card carries one extra line, and its "ULAGY SAÝLA" button was being
  clipped; the tile is taller now.

**Two changes for legibility rather than size.** The full sentence "Çykarylan
gollanma maglumatlarynda elýeterli däl" was printing on every empty spec row,
so a wagon card was four lines of *not available* and two of data; cards now use
a three-word form (`çeşmede ýok`) while spec sheets keep the full wording. And a
wagon that cannot be loaded now leads with **why** — its spec rows were all
empty anyway, and the reason is the thing the trainee needs to read.

# Logic pass — the arithmetic the tables exist for

Three rules that the data supported but nothing ever ran, plus the defects that
turned up while wiring them in.

## 1. A materials list (`consumables.dart`)

Every table needed for it was already in the app — chocks per layout case,
nails per chock (plate-06), wire, staples and strands per weight bracket
(TABLISSA No.1 on plate-03), the four-piece reusable sets — and **nothing ever
multiplied any of it out**. A trainee could finish a configuration without once
being told that four chocks means sixteen 6x200 nails.

`consumablesFor` now produces the bill for one vehicle from the method and the
layout case the trainee chose. A line whose quantity needs a figure the source
lacks is **listed anyway**, greyed, with what is missing named: dropping it
would understate the job. It appears at the end of the securing sequence.

## 2. Table 7 runs (`wire_lashing_angle.dart`)

The strand count is a grid lookup on two angles — lashing to the wagon's
longitudinal axis, lashing to the floor. Neither is a property of the vehicle,
so nothing in the catalogue could ever supply them and the check was hardcoded
to report UNKNOWN **for every configuration in the app**. The angles are now
measured on the wagon and entered per placement, and the table answers.

The floor-angle cap from the plate (45°) is checked separately and wins where it
and the table disagree — the table runs to 80°, the plate caps at 45 — and the
check says which one decided.

**A defect of mine, caught by reading the data's own note.** I first treated an
empty cell in Table 7 as a combination the handbook forbids, and reported it as
a FAIL. The table's note in `measurements.json` says the opposite: those cells
**were not legible when the plate was extracted**, and are not to be used
without checking the source page. Reporting one as forbidden would have been
this project inventing a handbook prohibition out of a bad scan. An empty cell
is now UNKNOWN and says why.

**Both handbook sources for the strand count are shown.** plate-03 gives it by
weight, Table 7 by angle, and they need not agree — at 26 t the weight table
says 8 strands where 30°/40° gives 2. Where they differ the materials list
names both and says the source page has to settle it, rather than printing one
as though it were the only one.

## 3. Axle load, decided one-sidedly

Where the limit, the weight and the axle count are known and the **average**
axle load already exceeds the limit, the load fails: the heaviest axle is at
least the average, so no distribution can save it. The converse stays UNKNOWN —
an average inside the limit says nothing about the heaviest axle, and the
extract records no distribution.

## Defects found while wiring these in

| Where | What was wrong |
|---|---|
| `weight_bracket.dart` | The bracket parser had no case for the `"<=45"` form Table 7 writes its angle bands in, so **every** lookup fell through to "outside the table" — the same silent-mismatch class as the Table 2 wordings fixed earlier. Operator forms (`<=`, `>=`, `<`, `>`) are handled now, and the doc says a new table's wording belongs here before it is read anywhere. |
| `engineering_validator.dart` | The wheeled branch added its own permanently-UNKNOWN Table 7 check. With the real one added by `evaluate`, one rule was reported twice, one of them undecidable by construction. Removed; the check is added once, for tracked and wheeled alike, and only where the configuration actually uses wire — asking a clamp-secured vehicle for its lashing angles would add an undecided check to a complete attempt, and an undecided check is never scored as correct. |
| `consist_providers.dart` | The measured angles are the first figures keyed by **placement** rather than by vehicle, so they are pruned with the other per-placement stores when a vehicle is removed or the train is rebuilt. A vehicle's weight is deliberately not: it belongs to the vehicle, and re-placing the same lorry should not mean retyping it. |
| `consumables_panel.dart`, `lashing_angle_entry.dart` | A citation chip is measured with unbounded width as a plain row child, and a label like "Madda 31 / Tablisa 11,13" pushed the row past its card — 25 px at 460 px wide, 105 px at 380. Both chips are bounded now and ellipsise inside their own box. |

## Verification

`flutter analyze` clean; **330 tests pass**. The layout defect above was found by
`test/securing_panels_widget_test.dart`, which pumps both new panels at 900 px
and at 460 px — an overflow throws in a widget test, so this catches on the
runner what the screenshot pass catches on a display, and catches it at a width
the screenshot pass never tried. `flutter build linux --debug` builds and the
binary starts clean on the nested display.
